# 구현 계획: 집필실 V1

기준 명세: [SPEC.md](../SPEC.md)

## 개요

어제 만든 시제품(V0)은 동작하지만 명세·단위 테스트 없이 만들었다. V1은 V0 코드를 버리지 않고,
명세의 성공 기준 1~7을 하나씩 **실패하는 테스트로 먼저 적고** 통과시키는 방식으로 다시 다진다.
테스트를 쓰다 드러나는 버그는 그 자리에서 재현 테스트와 함께 고친다.

## 설계 결정

- **V0 재사용**: `js/engine.js`의 문단 동기화, `js/store.js`, `scripts/build-studio.sh`, `studio/`·`vendor/`는
  그대로 쓴다. rhwp 연동은 이미 통합 테스트로 확인돼 있어 새로 짤 이유가 없다.
- **동기화 로직 분리**: 글자 차이 계산과 문단 대응 계획을 엔진 호출에서 떼어 `js/sync.js`의 순수 함수로 만든다.
  데이터를 잃을 수 있는 유일한 곳이라 단위 테스트로 경우의 수를 덮는다.
- **집필 화면 분리**: `js/app.js`에서 집필 동작을 `js/write.js`로 옮긴다. 동작은 바꾸지 않는다.
- **위험한 것 먼저**: 표 편집 자동화(성공 기준 5)는 rhwp 편집기 화면을 조작해야 해서 가장 불확실하다. 토대 다음에 바로 한다.
- **배포 제외**: GitHub Pages 설정과 공개 전환은 하지 않는다. 서비스 워커 코드는 남기되 V1 검증 대상이 아니다.

- [ ] 분리 전후로 기존 통합 테스트 결과가 같다

### 2단계: 성공 기준을 테스트로
- [ ] 작업 3: 표 편집(기준 5)
- [ ] 작업 4: 서식 보존(기준 3)과 글꼴 변경(기준 4)
- [ ] 작업 5: 글자 보존(기준 2)과 자동 저장(기준 7)

### 3단계: 집중 화면과 마무리
- [ ] 작업 7: 집필 화면 분리와 집중 동작(기준 1)

## 위험과 대비

| 위험 | 영향 | 대비 |
| --- | --- | --- |
| rhwp 편집기의 표 메뉴를 자동 조작하기 어렵다 | 중 | 편집기의 명령 실행 통로나 엔진 API로 같은 조작을 하고, 화면 조작으로 못 한 부분은 점검표에 수동 항목으로 적는다 |
| 편집기에서 준 서식이 집필 왕복 중 사라진다 | 높음 | 작업 4에서 가장 먼저 드러난다. 동기화가 바뀐 글자만 건드리는지 단위 테스트로 고정한다 |
| 편집기 시작 직후 문서가 안 그려지는 문제가 재발한다 | 중 | V0의 재시도 장치를 유지하고, 통합 테스트를 여러 번 돌려 확인한다 |
| 아이패드 Safari에서 한글 입력이 다르게 동작한다 | 높음 | 자동으로는 확인할 수 없다. 점검표 결과에 따라 후속 작업을 잡는다 |
